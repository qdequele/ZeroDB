# Sanctioned behavior divergences vs LMDB

Rules:
- Every entry needs a maintainer sign-off line. Agents may add entries only
  with status PROPOSED; a human flips them to APPROVED.
- Phase 1 goal is zero APPROVED functional divergences visible through heed,
  except the ones below.

| ID | Area | LMDB behavior | zerodb behavior | Status | Approved by |
|----|------|---------------|-----------------|--------|-------------|
| D-001 | Process model | Cross-process readers via lock file | Single-process only; no lock file | APPROVED | (founder decision, see PLAN.md rule 7) |
| D-002 | File format | LMDB 0.9/1.0 on-disk formats | Own format; migration via logical dump/load | APPROVED | (founder decision) |
| D-003 | Nested write txns | Child write txns with page shadowing | Unsupported — **unrepresentable in the public API** (no `Env::nested_write_txn`, no `RwTxn::nested`; a stronger form of the original "clean error", ADR-0007 Q2/Q3 amendment ratified 2026-07-16). The heed-zerodb adapter (M1.13) surfaces no nested-write entry point either — heed's own `RwTxn::nested` is `pub(crate)`. Zero call sites across all five consumers (SPEC 00 §A). Nested READ txns (fork semantics) ARE supported (M1.9, SPEC 04 §5). | APPROVED | Quentin, 2026-07-15 (chat: "go with your recommendations"); TXN-40 unrepresentability amendment: Quentin, 2026-07-16 (ADR-0007 Q2/Q3, session-lead review) |
| D-004 | DUPSORT/DUPFIXED, DatabaseFlags | Duplicate keys, integer keys, custom comparators | Unsupported in Phase 1 — no consumer uses any DatabaseFlags (SPEC 00 §B.1). Implemented in Phase 2.8. | APPROVED | Quentin, 2026-07-15 (chat: "go with your recommendations") |
| D-005 | Writer quiescence during nested read txns | The fork does not enforce it: a write txn may technically mutate while nested read children are live (undefined interplay; Meilisearch always pauses the writer by convention). | ZeroDB **enforces** writer quiescence for Rust soundness — while any nested read txn is live the parent write txn must not mutate: compile-time via the shared `&wtxn` borrow (SPEC 04 TXN-30) plus a runtime `child_count == 0` assert on every `&mut` op (SPEC 04 TXN-29). **Not observable to any consumer** — all six nested-read call sites (milli 5, hannoy 1) pause the writer already, so no functional divergence is visible through heed. | APPROVED | Quentin, 2026-07-16 (chat ratification queue). See SPEC 04 §5.2/§10. |
| D-006 | `map_size` value validation | heed (over LMDB) **rejects** any `map_size` not a multiple of the **OS** page size at open (`Io(InvalidInput)`: "map size (N) must be a multiple of the system page size"; observed 16384 on Apple Silicon). Discovered empirically in M1.2. | zerodb is **more lenient**: `EnvOpenOptions::map_size` stores the value and the read mmap covers the file length (kernel rounds), so any `map_size ≥ 2*page_size` is accepted regardless of OS page size. Rationale: zerodb's DB page size is deliberately independent of the OS page size (SPEC 02 §0, CLAUDE.md), and every consumer already clamps `map_size` to the page size before the call (`clamp_to_page_size`, SPEC 00 row 3), so the stricter check never fires in real use and the divergence is unobservable to consumers. Reproducing heed's exact OS-page-multiple check natively would require querying the OS page size (unsafe FFI / new dep) purely to reject inputs no consumer sends. The heed-zerodb adapter (M1.13) may re-impose the check at the heed boundary if the 1.14 gate requires exact parity. **Resolution (ADR-0004 OQ2, M1.4):** the env maps the full `map_size` at open, rounding the *mapping length* up to the OS-page multiple internally; the reported/persisted `map_size` and the MapFull predicate (SPEC 05 GC-17) use the exact configured value. | APPROVED | Quentin, 2026-07-16 (ADR-0004 OQ2 resolution, via session lead) |
| D-007 | FORK-1 crash case | SIGSEGV in `_mdb_cursor_put` (APPEND after same-txn clear of another db, key ≤ last — see docs/UPSTREAM-BUGS.md FORK-1) | Returns `KeyExist` per SPEC 01 §S1 — a crash is UB, not an observable behavior to replicate. Oracle skips the combination until the fork is fixed. | APPROVED | Quentin, 2026-07-17 (standing directive, session lead). Fork bug — see docs/UPSTREAM-BUGS.md FORK-1; guard removable once upstream fixes it. |
| D-009 | Concurrent `open_database` of a dropped-and-reused dbi | Opening a database **by name** in a fresh read txn while a *concurrent, still-open* write txn has **dropped and reused** that dbi's slot number returns the reused handle from the in-memory dbi table, then `mdb_get` through the read txn's stale dbi slot fails with `EINVAL` (`Io(InvalidInput)`). An LMDB dbi-reuse hazard. | zerodb resolves `open_database` purely from the transaction's **committed catalog** (SPEC 04 TXN-10): the just-created (uncommitted) name is absent → `Ok(None)`, the correct MVCC answer, no reused-slot hazard. **No consumer exercises this** — it requires a mid-write-txn `open_database` of a name whose dbi was dropped-and-recreated in that same open txn, read from a concurrent txn. The oracle's `VerifyGet` models a *post-commit* independent read, so `driver::classify` skips it while a write txn is open (`Skip::VerifyDuringWrite`); concurrent reader-vs-writer isolation is exercised via the M1.8 reader table. | APPROVED | Quentin, 2026-07-17 (standing directive, session lead). zerodb returns the correct MVCC answer; no consumer exercises the LMDB hazard. |
| D-008 | Raw bytes of a named-DB catalog record | Iterating/reading the **parent** DB (the unnamed root, or an outer named DB) surfaces each sub-DB's catalog entry with the sub-DB **record** as its value — LMDB's `MDB_db` struct layout (root pgno at offset 40, little-endian, packed). A consumer that raw-reads that value sees LMDB's bytes. | zerodb surfaces the same entry (same key, `F_SUBDATA`) but with **its own** `DBRecord` layout (SPEC 02 §3.1: root pgno at offset 0). The 48-byte value bytes therefore differ. **A direct consequence of D-002** (own on-disk format); observable *only* by raw-reading a sub-DB record through its parent, which **no consumer does** (milli's primary DB is the *named* `"main"`, so the root is a pure catalog it never reads as data; arroy/hannoy use only the unnamed root and never create named DBs, so their root has no catalog entries). The oracle models `DbName::Unnamed` as milli's named `"main"` so the fuzz never raw-reads a catalog record (see `op.rs`); the true unnamed-root path is covered without catalog mixing by `unnamed_root_differential.rs`. **Secondary:** DB **names** are byte strings in zerodb-core but C strings in heed (a name with an embedded `0x00` is a valid distinct DB in zerodb, unrepresentable in heed) — a heed adapter-boundary difference (M1.13), not a core one. | APPROVED | Quentin, 2026-07-17 (standing directive, session lead). Direct consequence of D-002; unobservable to all five consumers. |
| D-010 | `max_readers(0)` at env open | The fork **rejects the open**: `mdb_env_set_maxreaders(env, 0)` → `EINVAL`, surfaced by heed as `Io(InvalidInput)` ("Invalid argument", code 22). Observed empirically in M1.8 (probe against heed =0.22.1 / the fork, 2026-07-16). | zerodb **accepts the open** and sizes the reader table 0; every subsequent `read_txn`/`static_read_txn` fails with `MdbError::ReadersFull` (SPEC 04 TXN-16 applied per-txn instead of an open-time argument check). **No consumer passes 0** — Meilisearch sets 1024, the default is 126 — so the divergence is unobservable in real use. Kept as-is in M1.8 (no open-time validation added); the heed-zerodb adapter (M1.13) may re-impose the fork's open-time `EINVAL` at the heed boundary if the 1.14 gate requires exact parity. | APPROVED | Quentin, 2026-07-17 (standing directive, session lead). Re-imposed at the heed-zerodb boundary in M1.13, so consumer-visible parity is exact. |

| D-012 | Env data-file name | A directory env materializes as `<dir>/data.mdb` (+ `lock.mdb`); Meilisearch hardcodes the `data.mdb` name in **production** code — index compaction (`index-scheduler/.../process_batch.rs:707`, `meilisearch/.../routes/tasks/compact.rs:158`), snapshot creation (`process_snapshot_creation.rs:138,202,212`), S3 streaming (`enterprise_edition/s3.rs:238,301,311`), and meilitool offline compaction (`meilitool/src/main.rs:491`). Nothing in Meilisearch touches `lock.mdb` (grep: one doc comment only). | zerodb names its single data file **`zerodb.dat`** (SPEC 02 §8) and creates no lock file (D-001). **Not covered by D-002**, which sanctions the on-disk *format*, not the *filename*. Consequence on an adapter env today: compaction fails loudly (`fs::metadata("data.mdb")` → ENOENT), and snapshot restore is **silent data loss** (`copy_to_path(dst.join("data.mdb"))` succeeds, but reopening the restored dir finds no `zerodb.dat` and creates a fresh empty env). Latent behind a green M1.14 gate because index-scheduler ships no compaction/snapshot-restore round-trip test. **RESOLVED at the adapter boundary (ADR-0010, `docs/adr/0010-env-file-naming.md`, Option A)** — the M1.13 boundary-re-imposition pattern: the core keeps `zerodb.dat` as its native default, and `heed-zerodb` opens/creates `<dir>/data.mdb` via the plumbed `zerodb::EnvOpenOptions::data_file_name` option, so an adapter env dir contains exactly `["data.mdb"]`. No `lock.mdb` is ever created (nothing reads one; D-001 stands). All six production call-site families are correct: the `fs::metadata` compaction probe finds the file, and a snapshot dir written as `data.mdb` reopens with its contents instead of silently yielding a fresh empty env. The engine does **no** fallback probing (the adapter always reads the name it writes); `zerodb-tools` probes both names on read paths and treats both-present as a hard error. Contents remain ZeroDB's own format (D-002) — the `ZDB1` magic makes real LMDB reject an adapter file loudly, and `zerodb-tools stat` prints an engine-identification line. Covered by the two round-trip tests the consumer suites lacked (`crates/heed-zerodb/tests/env_file_naming.rs`: snapshot round-trip for both `CompactionOption`s, and the compaction `copy`+rename+close+reopen sequence), plus `crates/zerodb/tests/data_file_naming.rs`, `crates/zerodb-tools/tests/data_file_probe.rs`, and the extended oracle garbage-file differential. | **APPROVED** — resolved; no standing divergence remains at the heed boundary | Quentin, 2026-07-20 (standing directive, session lead), implemented per ADR-0010 |
| D-011 | `MDB_envinfo::me_numreaders` semantics | The counter is a **high-water mark, not a live count**: `mti_numreaders` is only ever *incremented*, and only when the first-fit slot scan lands past the current high-water (`if (i == nr) ti->mti_numreaders = ++nr;`). Ending a read txn clears the slot's `mr_pid` but leaves the counter alone, so `me_numreaders` reports the **maximum number of simultaneously live readers ever observed** by the env and never decreases. LMDB's own header documents it as "number of reader slots used", which is misleading. Discovered empirically in M2.1 (differential probe, 2026-07-20), then confirmed against the fork's `mdb.c`. | zerodb **reproduces LMDB exactly** (`EnvInfo::num_readers` = the same monotone high-water, maintained by a `fetch_max` at slot claim; `crates/zerodb-core/src/readers.rs`). Because the LMDB number is rarely the one a caller wants, zerodb **additionally** exposes the genuinely-live count as the new field `EnvInfo::live_readers` (and `heed_zerodb::Env::live_readers()`, a method rather than an `EnvInfo` field so heed's mirrored struct keeps its exact shape). No existing behavior changes; the extension is purely additive. | **PROPOSED** — Phase 3 candidate: *should `num_readers` be redefined to the live count once Phase 1/2 parity obligations lapse?* Not approved; parity is currently exact. | — (agent-filed, M2.1; awaiting maintainer) |
| D-013 | dbi handle validity after an aborted txn | A `Database`/dbi handle **dies with the transaction that opened it**. `lmdb.h` (`mdb_dbi_open`): "The database handle will be private to the current transaction until the transaction is successfully committed. If the transaction is aborted the handle will be closed automatically." `mdb.c` implements this in `mdb_dbis_update(txn, keep)` from `mdb_txn_end`: on the non-commit path every dbi flagged `DB_NEW` has `me_dbflags[i]` cleared and `me_dbiseqs[i]` bumped. Re-using such a handle then fails the `TXN_DBI_EXIST(txn, dbi, DB_VALID)` gate at the top of `mdb_cursor_open` (and `DB_USRVALID` in `mdb_put`) and returns **`EINVAL`**. Separately `mdb_drop(txn, dbi, del=1)` calls `mdb_dbi_close` directly — an env-level close a later abort does **not** undo. | ZeroDB's `Database` is a **plain value** (name + root), not a slot in an env-level dbi table carrying a validity flag and sequence number, so it has no way to go stale: re-using a handle whose creating txn aborted silently works instead of erroring. Discovered 2026-07-20 by the adapter-pair differential fuzzer, which reached the state via a harness bookkeeping defect (a positional `committed_dbs` watermark that `drop_db`'s middle-removal invalidated); **the harness was fixed** (per-entry `committed` flag, `crates/zerodb-oracle/tests/dbi_handle_lifetime.rs`) so the oracle no longer drives use-after-close, and both fuzz pairs are green. What remains is this latent leniency on usage that LMDB defines as invalid. No consumer relies on it: milli/hannoy create their databases in a txn they commit, and using a handle from an aborted txn is a bug in consumer code either way. Re-imposing it would require giving the engine an env-level handle registry with generation counters — a real design change, not a boundary check, hence not done unilaterally. | **PROPOSED** — NOT approved. Maintainer decision needed: should ZeroDB (or the `heed-zerodb` boundary) track dbi-handle generations so a handle from an aborted txn errors like LMDB's `EINVAL`, or is this leniency acceptable given no legal usage can observe it? | — (agent-filed 2026-07-20, adapter-pair fuzz finding; awaiting maintainer) |
| D-014 | Custom key comparator persistence | `mdb_set_compare(txn, dbi, fn)` installs a C function pointer **per dbi, per open**, and LMDB writes **nothing** about it to the file. Reopening a database with a different comparator than the one that built it is undefined in practice: searches descend wrongly, `mdb_get` misses present keys, and writes interleave two orderings into one tree. LMDB detects none of this — there is no comparator identity in `MDB_db` to check against. | ZeroDB **reproduces the hazard** (M2.4, SPEC 03 §2.0/§2.0.1): the comparator lives in the env's in-memory `ComparatorRegistry`, keyed by dbi, and is never persisted. Two mitigations LMDB lacks: (1) the **in-process** case is detected — a second registration for the same database with a different `Comparator::name` is refused with `Io(InvalidInput)` rather than silently taking one; (2) the feature is confined to **named** databases, so a bad comparator can corrupt one user DB but never the catalog or the GC tree. The **cross-open** case is not detected and cannot be without an on-disk format change: `DBRecord` is exactly 48 bytes with every offset assigned (SPEC 02 §3.1), and its only two unused values — `flags` (offset 42) and `leaf2_ksize` (offset 44) — are already reserved for DUPSORT/DUPFIXED in M2.8. A comparator fingerprint would mean widening the record or repurposing those fields, i.e. an on-disk format decision, which CLAUDE.md rule 6 puts behind an ADR and human approval. Not taken unilaterally. **No consumer is affected** — all five use `DefaultComparator` (SPEC 00 row 53), so nothing in the Meilisearch tree can reach this. | **PROPOSED** — NOT approved. Maintainer decision needed: *should a comparator-identity fingerprint be added to the on-disk per-DB record (a format change, hence an ADR + `format_version` bump), so that reopening under the wrong ordering fails loudly at open instead of corrupting silently?* Parity with LMDB is currently exact; the question is whether to be **better** than LMDB here. | — (agent-filed 2026-07-20, M2.4; awaiting maintainer) |

### M1.13 adapter-boundary re-impositions (2026-07-17)

The core engine keeps its lenient native behavior (the divergences above stand
as filed); the **`heed-zerodb` adapter now re-imposes the fork's stricter
behavior at the heed boundary** so the 1.14 gate sees exact parity, each with a
test in `crates/heed-zerodb/tests/boundary.rs`:

- **D-006** — `EnvOpenOptions::open` rejects a `map_size` that is not a multiple
  of the OS page size (`sysconf(_SC_PAGESIZE)`) with `Io(InvalidInput)`.
- **D-010** — `EnvOpenOptions::open` rejects `max_readers(0)` with
  `Io(InvalidInput)` before touching the engine.
- **D-008 (secondary)** — a DB name with an embedded NUL reproduces heed's
  `CString::new(name).unwrap()` **panic** (the fork's observable behavior, probed
  against heed =0.22.1's `raw_open_dbi`), rather than inventing a clean error.

Additionally, the LMDB **read-key size taxonomy** (SPEC 03 §2.1 — the leniency
the core defers to "the caller", D-004/SPEC 03 note) is applied in the adapter's
read path: an **empty** key → `MdbError::BadValSize` on
`get`/`delete`/neighbor-seeks/forward-`prefix_iter` (an oversized read key is
still not rejected). Not a new divergence — it closes the read-side leniency the
core intentionally left to the heed boundary. No consumer sends empty keys, so
none of these fire in real use; they exist for exact fork parity.
