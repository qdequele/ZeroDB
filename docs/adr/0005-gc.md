# ADR-0005: GC implementation — in-txn structures, freelist_save at C1, reclaim wiring

- Status: Approved — Quentin, 2026-07-16, standing directive, reviewed by
  session lead. OQ1–OQ4 answered; resolutions recorded at the end of this
  document.
- Milestone: 1.5
- Date: 2026-07-16

## Context

M1.5 fills the two seams ADR-0004 left open: the `freelist_save` stub at the C1
hook of `commit_pipeline` and step 2 of `allocate` (the GC draw), both in
`crates/zerodb-core/src/rwtxn.rs`. The **algorithm is not up for debate** — it
is fully specified in SPEC 05 (GC-1..28) and this ADR does not redesign it.
What is decided here is the *implementation strategy*: in-txn data structures,
the exact code-reuse seam for mutating the GC tree, where the allocation-mode
restriction lives, how the check tool flips INV-10/INV-22 on, and the concrete
acceptance tests for PLAN 1.5 (bounded growth + LMDB tolerance band).

Fixed inputs:

- **SPEC 05** — GC DB = ordinary B+tree of `BE(txnid) → PIL` entries over
  normal `P_LEAF`/`P_BRANCH` pages (GC-1..5, SPEC 02 §7); a txn records
  `freed_pgs`/`loose_pgs` (GC-6..10); `freelist_save` = apply_drains →
  trailing-loose shrink → loop-until-stable with **all GC draws barred**
  (GC-11..13); allocation order loose → GC → extend (GC-14..17, GC-28);
  oldest-reader gate + ascending scan + deterministic pick (GC-18/19);
  partial-drain remainder rewrite (GC-20); within-PIL-only run search (GC-21);
  `non_free_pages_size` exact walk (GC-22..24); huge-txn weakness documented,
  baseline measured, not fixed (GC-25..27). Check invariants INV-22..27.
- **SPEC 04 §9** — C1 is the landing site: `freelist_save` runs before any
  dirty page is written (C2), so every GC mutation rides the txn's dirty set
  and vanishes atomically on a crash-fallback to `N−1` (GC-14, REC-6 H0).
- **SPEC 04 TXN-20/21 + SPEC 03 §8 note (interim gate)** — until M1.8's reader
  table exists, `oldest_reader()` degenerates to `writer_txnid − 1` ("oldest
  reader = current txn"): a GC entry keyed by `F` is reclaimable iff
  `F ≤ writer_txnid − 1`, i.e. **freeing txnid < current txnid**, with no
  reader table consulted because none exists yet.
- **ADR-0004 seams** — `RwTxn { freed, loose, next_pgno, committed_last_pg,
  free_db, .. }` already accumulates GC-6/7 faithfully; `allocate` is
  loose-then-extend; C1 currently runs only `release_trailing_loose()`; the C2
  `debug_assert(pgno > committed_last_pg)` is the M1.4 form of TXN-62 and must
  be generalized; `check_image` skips INV-10/22 (ADR-0004 OQ4 leak window).

Prior art consulted clean-room (algorithms only): LMDB fork
`mdb_freelist_save` (retry loop keyed on the freed list growing),
`mdb_page_alloc` (`me_pghead` — the env-level candidate IDL that *merges
several freelist entries* while hunting contiguous runs, `mdb_midl_xmerge`),
`mt_loose_pgs`; libmdbx GC (`relist`, spill/unspill, and the "BigFoot"
huge-PIL splitting that is our Phase 3.1 direction, explicitly rejected for
Phase 1 by GC-27).

---

## D1 — In-txn GC structures and the btree code-reuse seam

The GC tree MUST be mutated by the **same** split/merge/COW code as the main
tree (its pages are structurally identical, SPEC 02 §7; two btree writers
would be the exact drift hazard ADR-0004 D2 rejected). Today every write op in
`rwtxn.rs` hardcodes `self.main_db` (~30 sites: root/depth/stat updates in
`put_main`, `delete_main`, `insert_into_leaf/branch`, rebalance, root
grow/shrink).

**Options.**

- **A — tree-selector parameter (chosen).** Add `enum TreeId { Main, Free }`
  and `fn record(&self, t) -> &DBRecord` / `fn record_mut(&mut self, t) ->
  &mut DBRecord`; thread `tree: TreeId` through the internal mutation path
  (`put_tree(tree, key, flags, val)`, `delete_tree(tree, key)`, descent,
  split, rebalance). `put_main(k, f, v)` becomes
  `put_tree(TreeId::Main, ..)` — public API unchanged. Mechanical refactor,
  no borrow-checker friction (everything already goes through `&mut self`),
  and it is the exact seam M1.6 (named DBs) extends to a catalog-backed
  `TreeId::Named(..)` — the refactor is paid for twice.
- **B — extract free-standing `TreeOps` borrowing `(&mut DirtyStore, &mut
  DBRecord, &mut Allocator)`.** Cleaner on paper, but `allocate`/`free_page`
  need `loose`/`freed`/`next_pgno`/`drains` while tree ops hold the disjoint
  borrows — requires split-borrow plumbing or a context struct that
  restructures all of `rwtxn.rs` for no M1.5 behavior gain. Deferred; can be
  revisited at M1.6 if `TreeId` proves cramped.
- **C — a bespoke minimal GC-tree writer.** Rejected outright: two btrees to
  keep in sync (ADR-0004 D2's argument), and GC pages would drift from INV-1..9.

**In-txn structures (chosen shapes + why):**

| Field | Type | Role |
|---|---|---|
| `freed` | `Vec<u64>` (exists) | GC-6 freed set. Append-only during ops; sorted + `debug_assert`-deduped at each loop-(c) encode (GC-3/4). Vec, not BTreeSet: appends are the hot path, sorting is once-per-commit-iteration. |
| `loose` | `Vec<u64>` (exists) | GC-7/8 LIFO fast path; unchanged. |
| `drains` | `BTreeMap<u64 /*F*/, Vec<u64> /*remaining, sorted*/>` (new) | GC-20 bookkeeping between `allocate` and `freelist_save`. First reclaim touching entry `F` decodes its PIL out of the tree into `remaining`; every draw pops from `remaining`; `apply_drains` rewrites (`remaining` non-empty) or deletes (`empty`) entry `F`. `BTreeMap` because the GC-18 scan wants ascending-`F` iteration and the map is small (entries touched this txn only). |
| `reclaimed` | `HashSet<u64>` (new) | Every pgno handed out by a GC draw this txn. Serves two masters: (1) the generalized TXN-62 assert at C2 (`pgno > committed_last_pg || reclaimed.contains(pgno)`); (2) correct loose classification — `free_page` currently classifies loose by `pgno > committed_last_pg`, but a reclaimed page re-freed in the same txn is also this-txn-private (it was drained out of `F`, no committed snapshot ≥ the gate references it), so the loose test becomes `pgno > committed_last_pg || reclaimed.contains(pgno)`. (A reclaimed pgno is ≤ `committed_last_pg`, so it can never trigger the GC-10 trailing shrink — no interaction.) |

The GC key codec is the existing M1.1 `geometry::gc_key_encode/decode`
(BE-u64, GC-2); PIL encode/decode (`u64 count + c×u64` LE, GC-3) is a small
new `page`-module helper shared by `rwtxn`, `check`, and the
`non_free_pages_size` walk. `gc_reclaim` *reads* the free_db tree through the
existing read `Cursor` over `Source::Writer` (dirty-first), collecting
`(F, PIL)` into owned buffers before mutating `drains` — no borrow conflict.

## D2 — `freelist_save` at C1: insertion, loop mechanics, alloc-mode switch

**Insertion.** The C1 block in `commit_pipeline` becomes exactly one call,
`self.freelist_save()?`, which encapsulates the GC-11 order internally —
including the trailing-loose shrink the stub used to call directly:

```
freelist_save(&mut self):
    debug_assert!(alloc_mode == Normal); alloc_mode = GcSave      # GC-12 scope
    (a) apply_drains: for (F, remaining) in take(drains):         # GC-20
            if remaining.is_empty(): delete_tree(Free, BE(F))
            else: put_tree(Free, BE(F), encode_pil(remaining))    # rewrite
    (b) release_trailing_loose()                                  # GC-10
    (c) loop:
            before = freed.len()
            if freed.is_empty() && no entry BE(txnid) exists: break
            put_tree(Free, BE(txnid), Reserve(pil_size(freed)))   # encode in place
            if freed.len() == before: break                       # fixed point
    debug_assert!(iterations <= FREELIST_SAVE_MAX_ITERS)          # GC-13 guard
```

- **Alloc-mode switch — options.** (i) an `alloc_mode: AllocMode` field on
  `RwTxn` (`enum AllocMode { Normal, GcSave }`), checked once at `allocate`
  step 2 (chosen — one field, one branch; `freelist_save` runs once at the end
  of the txn's life so no restore/RAII is needed, and a `debug_assert` in
  `gc_reclaim` that the mode is `Normal` catches any future misuse);
  (ii) threading a `bool in_save` parameter through
  `put_tree → insert → split → touch → allocate` (rejected: pollutes ~15
  signatures to express one txn-global phase); (iii) typestate `RwTxn<Saving>`
  (rejected: the pipeline needs `&mut self` mid-commit, not a type change).
- **GC-12 scope**: the mode is set before step (a) and never cleared —
  steps (a), (b), (c) all allocate loose-or-extend only, so the consumed-entry
  set is frozen at exactly the drains recorded during the txn, which is what
  makes step (a)-once sound and GC-13's termination argument hold.
- **Loop mechanics**: each iteration sorts+dedups `freed`, computes the PIL
  byte size, and upserts under the same key `BE(writer_txnid)` using the
  RESERVE path (encode straight into the leaf cell or overflow frame — no
  double buffering of a potentially multi-MB PIL, GC-5). An iteration that
  splits GC leaves or replaces a spilled PIL's overflow run pushes the
  obsoleted GC pgnos onto `freed` via the ordinary `free_page`/`free_run`
  (GC-6 bullet 4 — no special case), which is what the fixed-point test
  observes. `FREELIST_SAVE_MAX_ITERS` is a generous constant (e.g. 32) turning
  a GC-13 regression into a loud debug panic instead of a hang.
- **Crash safety at every cut**: `freelist_save` mutates *only* dirty frames
  and the in-memory `free_db` DBRecord — nothing reaches disk before C2, so a
  crash anywhere inside C1 recovers to `N−1` byte-identically (GC-14,
  REC-6 H0). Between C2 and C5, pages drained from entry `F` may have been
  overwritten on disk, but the fallback meta `N−1` still holds the *old*
  free_db root whose entry `F` still lists them as free and whose main tree
  does not reference them (gate: `F ≤ N−1`) — consistent either way (TXN-62).

## D3 — Allocate step 2: `gc_reclaim` wiring

`allocate(n)` gains its middle step, verbatim GC-16 order:

```
1. loose fast path (n == 1)                                   # unchanged
2. if alloc_mode == Normal:                                   # GC-12 skip
       if let Some(run) = gc_reclaim(n): return run
3. extend with the GC-17 MapFull predicate                    # unchanged
```

- **Gate (interim, cite SPEC)**: `oldest = self.txnid − 1` — the SPEC 04
  TXN-21 pre-M1.8 degeneration ("oldest reader = current txn", SPEC 03 §8
  note): an entry `F` is reclaimable iff `F < writer_txnid`, i.e. freed by any
  *committed* txn, because no reader table exists yet. M1.8 replaces this one
  expression with the TXN-20 slot scan; nothing else in `gc_reclaim` changes.
  The soundness caveat of this placeholder is OQ1 below.
- **Scan (GC-18)**: forward cursor over free_db from `first()` (BE keys ⇒
  ascending txnid); for each `F ≤ oldest`, resolve the working id list —
  `drains[F]` if present (already touched this txn), else decode the tree PIL.
  Entries whose `remaining` is empty are skipped (deleted later by
  `apply_drains`, never mid-ops).
- **Pick determinism (GC-19)**: `n == 1` → smallest id of the smallest
  reclaimable `F` (front of the sorted `remaining`). `n > 1` → linear
  contiguous-run scan of each candidate's sorted `remaining` (GC-15/GC-21:
  **within one PIL only** — no cross-entry merging; note this is deliberately
  *less* capable than the fork's `me_pghead` xmerge and is the spec'd Phase 1
  parity-with-fragmentation policy, absorbed by the D5 tolerance band). The
  drawn ids are removed from `remaining` and inserted into `reclaimed`; the
  entry stays in the tree untouched until `apply_drains` (GC-20 — never
  literal-delete a partially drained entry, never leave a drained id behind).
- **TXN-62 generalization at C2**: the M1.4
  `debug_assert!(pgno > committed_last_pg)` becomes
  `debug_assert!(pgno > committed_last_pg || reclaimed.contains(&pgno))` —
  precisely "beyond the old high-water, or reclaimed under the gate".

## D4 — Flipping INV-10/INV-22..27 on in `check_image`

**Mechanics**: `check.rs` already collects `visited` (every reachable page
incl. overflow interiors and both trees' own pages) and already validates GC
entry shape (INV-23/25/26 live since M1.4). Add: `check_gc_entry` records the
decoded ids into a `free: HashMap<u64, count>`; after both `check_record`
walks, assert the partition of `[FIRST_DATA_PGNO, last_pg]`:
`visited ∩ free = ∅` (reused-while-listed), `visited ∪ free = all` (leak),
each id free at most once across entries (INV-24, sharper diagnostic than the
partition failure). INV-27 is asserted at the API level (a test comparing
`non_free_pages_size()` against the walk's sums), not inside `check_image` —
the image walk has no `fstat`.

**M1.4-era images — regenerate vs annotate (options).**

- **A — flip on unconditionally (chosen).** Verified: the repo contains **no**
  committed `.dat` fixtures; every test image is produced at test time by the
  builder (fresh trees, empty GC — INV-22 holds trivially) or by real commits
  through the *current* write path; the fuzz corpus is op-encoded and replays
  through current code. So "regenerate" is automatic and free. Env files
  created by an M1.4 binary would report INV-22 leak violations under the
  M1.5 check tool — correct behavior (they *do* leak); pre-release dev files
  carry no compatibility promise and the ADR-0004 OQ4 note already said the
  leak window ends here.
- **B — a `CheckOptions::skip_reach_xor_free` escape hatch.** Rejected: it is
  a standing invitation to weaken the strongest invariant the tool has
  (CLAUDE.md rule 2 in spirit), for files nobody keeps.

The M1.4 scope-note comments in `check.rs`/`rwtxn.rs` ("leak window",
"INV-10/22 excluded") are deleted in the same change, and the per-fuzz-case /
per-proptest invariant walk inherits the full check automatically.

## D5 — Acceptance: bounded growth + LMDB tolerance band + long-fuzz bound

PLAN 1.5 acceptance is behavioral, so the tests are concrete and pinned here:

1. **Churn parity test** (`zerodb-oracle`, `#[test]` + a `just`-runnable long
   variant): identical workloads driven into the fork (via heed) and zerodb,
   both at psize 4096 (the fork's fixed size), same 64 MiB map. Workload per
   cycle: insert `K = 1000` keys (values 50–2000 B, ~1/8 overflow-sized),
   delete a random half (seeded RNG, same seed both engines), commit;
   `C = 200` cycles; record `real_disk_size` after every commit → two growth
   curves.
   - **Boundedness (the real acceptance)**: zerodb's curve reaches steady
     state — `size(cycle 2c) ≤ 1.05 × size(cycle c)` for all `c ≥ C/4`. A
     freelist leak or a reclaim that never fires shows up here as a linear
     ramp, regardless of what LMDB does.
   - **Tolerance band**: final steady-state zerodb size within
     **[0.5×, 1.5×] of LMDB's**, and for a *single-page-values-only* variant
     (no overflow) a tighter **±25 %**. Justification for the asymmetric,
     generous general band: (i) 32-byte page header vs LMDB's 16 and a
     32-byte overflow header vs 16 — ~0.4–3 % steady overhead plus an
     occasional extra overflow page per large value; (ii) different split
     fill policy (SPEC 03 §6.4 median-fit vs LMDB's split heuristics) — up to
     ~10 % page-count difference under churn; (iii) the dominant term:
     GC-21's within-PIL-only run search vs the fork's cross-entry `me_pghead`
     merging means zerodb can extend the file for an overflow run where LMDB
     reuses fragmented space — spec-sanctioned (Phase 3.1 fixes it), so the
     overflow-bearing band must absorb it; the no-overflow variant removes
     (iii), hence ±25 % there. Numbers are proposals — OQ3.
2. **Huge-txn baseline (GC-26)**: one measured run past the spill threshold
   (≥ 251 freed pages in one txn at psize 4096): record file size and
   per-commit `freelist_save` time into the PROGRESS note as the Phase 3.1
   baseline. Measurement only, no assertion beyond completion + clean walk.
3. **Long-fuzz bound assertion**: `diff_ops` already walks the committed image
   per case (now with INV-22, catching every leak/double-listing
   structurally). Add to the per-case epilogue: zerodb `real_disk_size ≤
   BASE + 1.5 × lmdb_real_disk_size` (BASE = a few pages of fixed overhead) —
   a cheap cross-engine growth tripwire on every one of the ~10-min gate's
   runs, complementing the deterministic churn test.
   - *BASE as implemented (review finding 3, 2026-07-16):* **72 pages
     (288 KiB)**. The deterministic minimum is 65 pages, set not by fixed
     overhead but by a **measured sequential-plain-put fill-factor
     divergence** surfaced the first time file sizes were compared: on 400
     ascending ~500-byte-key inserts zerodb's §6.4 median split yields ~50 %
     leaves (132 pages) where the fork's `mdb_page_split` splits at the
     insert point (~68 pages) — a true ~2× leaf-page ratio on ascending
     workloads (peak 263 vs 132 pages through the delete cascade; GC reuse
     verified exactly flat across generations, so this is a SPEC 03 §6.4
     split-heuristic question, **flagged for triage**, not a GC defect).

## D6 — Risk register (top 3 traps and the guard test each)

1. **Freelist-writes-to-itself under-accounting** — a GC page freed *by* the
   step-(c) put (split donor, replaced overflow run of a spilled PIL) missing
   from the PIL finally written, or a draw inside `freelist_save` consuming a
   page the rewritten entry still lists (the GC-12 leak). Guard: a
   deterministic test that pre-loads hundreds of small GC entries (many churn
   commits), then commits a txn whose freed set forces GC-leaf splits *and* a
   PIL spill during step (c), then runs the full INV-22 walk (a leaked page =
   "neither reachable nor free", a double = "both") + the
   `FREELIST_SAVE_MAX_ITERS` assert; plus `debug_assert(alloc_mode == GcSave ⇒
   no gc_reclaim)` compiled into every draw.
2. **Double-free / reuse-while-referenced** — a drained id handed out twice
   (drain bookkeeping desync between `drains` and the tree), or reclaiming a
   page a live snapshot still references (gate bug). Guard: INV-22/24 on every
   fuzz case and after every proptest commit (structural detection); a
   targeted test that partially drains one entry across several allocations,
   commits, reopens, and re-drains the remainder (exercises
   drains-vs-rewritten-tree agreement across commits); and the differential
   itself — a reused-while-referenced page corrupts committed reads and
   diverges from the oracle immediately.
3. **Remainder-rewrite loss (GC-20)** — deleting a partially drained entry
   (leaks the remainder) or failing to remove drained ids (re-hand-out).
   Guard: a deterministic partial-drain test asserting, post-commit and
   post-reopen: the remainder ids are still GC-listed (INV-22's "never
   neither"), the drained ids are not (INV-24 / "never both" — they are now
   reachable), and a follow-up txn allocating exactly the remainder's size
   does **not** grow `real_disk_size` (proves the remainder is actually
   reusable, not just listed).

Crash-interleaving of all of the above is covered structurally: every GC
mutation is dirty-set-only until C2 (D2), so the existing H0–H4 crash-smoke
matrix extended with a churn-workload variant (crash mid-commit *after* many
GC-reclaiming commits, reopen, full INV-22 walk) closes the loop until M1.11's
full harness.

## Consequences

- `rwtxn.rs`: `TreeId` refactor of the mutation path (mechanical, ~30 sites);
  new fields `drains`, `reclaimed`, `alloc_mode`; `freelist_save` replaces the
  stub (absorbing `release_trailing_loose`); `allocate` step 2; `free_page`
  loose-classification and C2 assert generalized. `zerodb-core` stays
  `#![forbid(unsafe_code)]`, miri-clean (all new logic is I/O-free).
- `page`: shared PIL encode/decode helper (GC-3) next to the existing GC key
  codec.
- `check.rs`: free-set collection + INV-22/24 partition; M1.4 scope notes
  deleted; INV-27 via an API-level test.
- `zerodb`/`zerodb-core`: `non_free_pages_size()` (GC-23 walk under a read
  snapshot) if OQ4 is accepted into M1.5 scope.
- Oracle: churn parity test + long variant, huge-txn baseline run, fuzz
  epilogue size tripwire; crash-smoke churn variant.
- M1.6 inherits `TreeId` as the named-DB seam; M1.8 replaces exactly one
  expression (the interim `oldest`); Phase 3.1 gets its measured baseline.
- SPEC touch-ups in the same change (rule 3, flagged in OQ2): align GC-11's
  inline pseudocode comment with GC-12's tightened rule.

## Open questions for human review

1. **Pre-M1.8 reader-soundness window (D3 gate).** The spec'd interim gate
   (`oldest = writer_txnid − 1`, TXN-21/SPEC 03 §8) assumes *no readers*, but
   the M1.4 read API is live: a `RoTxn` held across a later write commit can
   pin a snapshot older than `writer − 1`, and M1.5 reclaim could overwrite a
   page that reader still references — a real unsoundness window until M1.8,
   reachable only by holding a read txn across a concurrent committing writer.
   Options: **(a)** accept as spec'd — document loudly on `Env::read_txn`,
   keep the oracle/tests single-txn-at-a-time (their current shape), fix in
   M1.8 (this is what SPEC currently says; PLAN sequences 1.5 before 1.8
   knowingly); **(b)** a ~30-line interim gate now — `Mutex<BTreeMap<txnid,
   usize>>` refcounted in `read_txn`/`Drop`, `oldest = min(map.keys.first(),
   writer−1)`, deleted wholesale by M1.8. Recommendation: **(b)** — it is
   small, obviously correct (mutexed, no atomics ordering to review), keeps
   the tree sound for any user of the public API in the interim, and does not
   pre-empt M1.8's lock-free design. Needs your call because it exceeds the
   letter of the SPEC placeholder (spec wins until amended — if approved, the
   SPEC 03 §8 / TXN-21 interim notes get a one-line amendment in the same
   change).
2. **GC-11 vs GC-12 internal inconsistency (spec touch-up).** GC-11's
   pseudocode comment still says the in-loop allocator "may draw … from GC
   entries already drained THIS commit", but GC-12 (and GC-13's "tightened
   rule" remark) bars **all** GC draws for the whole of `freelist_save`.
   GC-12 is clearly the operative rule (it is titled the anti-leak rule and
   GC-13's proof relies on it); proposal: fix the GC-11 comment to
   "loose pages or file extend only" in the same change. Approve?
3. **Tolerance numbers (D5).** Proposed: steady-state flatness ≤ 1.05×
   half-to-full; LMDB band [0.5×, 1.5×] general, ±25 % for the no-overflow
   variant; fuzz tripwire ≤ BASE + 1.5× LMDB. Are these bands acceptable as
   the PLAN 1.5 "tolerance band", or do you want them tighter (at the cost of
   flakiness from the spec-sanctioned GC-21 fragmentation gap)?
4. **Is `non_free_pages_size()` in M1.5 scope?** SPEC 05 §7 (GC-22..24) is a
   SPEC 00 MUST (rows 18/19, milli's auto-resize trigger) and becomes
   implementable the moment the GC DB exists; PLAN does not assign it to a
   milestone explicitly. Recommendation: include it here (a ~40-line read-only
   walk + the INV-27 test); the alternative is parking it until the heed
   adapter (M1.13) forces it.

## Open questions — RESOLVED (Quentin, 2026-07-16, standing directive, via session lead)

2. **OQ2 — GC-11 pseudocode comment: APPROVED.** Fixed in the same change to

4. **OQ4 — `non_free_pages_size()`: APPROVED for M1.5**, plus

## Implementation finding — GC-12 amendment (2026-07-16) — RATIFIED

Ratified — Quentin, 2026-07-16, standing directive; independently confirmed
by adversarial review that the pre-amendment rule and PLAN §1.5 bounded
growth are mutually exclusive. SPEC 05 GC-11 pseudocode rewritten to the
ratified design in the same change (review finding 1).

The D6 guard tests caught that GC-12 **as originally written** ("ALL GC draws
barred during `freelist_save`") makes PLAN §1.5's bounded-file-growth
acceptance unachievable: the in-save COW of a committed GC page can never
reuse its own predecessor in the same commit (TXN-62 — the `N−1` meta still
references it), so under the total ban every commit's GC-tree writes extend
the file, while the obsoleted GC pages are only consumable by next-txn ops
draws; on steady churn ops allocations balance ops frees, so the file leaks
upward by the per-commit GC-COW count forever (measured ≈ +1 page/commit;
the steady-state churn guard failed 233472 → 266240 over 30 cycles). The
fork is bounded precisely because `mdb_page_alloc` inside `mdb_freelist_save`
consumes the already-loaded `me_pghead` while never reading fresh FreeDB
entries — the behavior GC-11's original pseudocode comment described before
the M0.4 spec-review tightened it into GC-12.

**Amendment implemented (SPEC 05 GC-12/GC-13 updated in the same change,
marked pending ratification):** in-save `allocate()` still never *reads* the
GC tree, but may draw from the txn's already-loaded drain pool; every entry
so touched returns to the pending-rewrite set, and the C1 loop's fixed point
(no pending rewrites + `freed` stable + loose settled) now carries the
anti-leak property the ban existed for. Gate correctness is inherited (pool
entries passed `F ≤ oldest_reader()` at load; later readers pin
`≥ writer_txnid − 1 ≥ F`). Termination: every non-exiting iteration strictly
shrinks the pool, COW-frees a committed GC page, or folds a loose page —
all bounded. With the amendment, all D6 guards pass (steady-state flatness
included). **A human must ratify or overturn this GC-12/GC-13 amendment; if
overturned, M1.5's bounded-growth acceptance criterion must be re-scoped.**

## Implementation note recorded during D2 bring-up (same change)

GC-13's fixed point is only reachable if the pages of the *previous loop
iteration's* PIL value (freed when the step-(c) upsert replaces it) are
**re-allocatable inside the loop** rather than folded into `freed` — folding
them would grow the PIL every iteration and diverge. They are this-txn-private
(extend/loose-allocated during the save), so they classify as loose (GC-7),
and the loop's allocator serves them back — including as a **contiguous run**
(with top-of-file extension when the run abuts `next_pgno`) for a re-spilled
PIL, the analogue of the fork's same-txn `mdb_ovpage_free` unallocate path.
GC-16's "loose = single-page only" rule continues to govern **Normal**-mode
allocation; the run-capable loose draw exists only inside `freelist_save`
(GcSave mode), where GC-12 already restricts sources to loose/extend. Leftover
loop-loose pages are re-checked by a final trailing shrink after the fixed
point; any survivors are folded into `freed` and the loop resumes (each fold
consumes its pages permanently, so this terminates; the `MAX_ITERS` assert
guards). SPEC 05 GC-12 annotated accordingly in the same change (rule 3).

## D5 addendum — end-of-page insert-point split adopted (2026-07-16) — RATIFIED

Ratified — Quentin, 2026-07-16, standing directive. D5's split-heuristic
triage item (recorded above: "flagged for triage", "a SPEC 03 §6.4 split
heuristic question, not a GC defect") is now resolved by adopting the fork's
insert-point split for end-of-page inserts. SPEC 03 §6.4 amended in the same
change (with the pre-amendment text preserved); this addendum records the
decision and the new measurements.

**The change.** When a leaf insert lands at the END of the page
(`newindx == nkeys`, i.e. the new key is greater than every key on the page)
and forces a split, zerodb now splits **at the insert point**: all existing
cells stay on the left (dirty) page and the new cell alone starts the right
page (`s = nkeys`). This was previously APPEND-only (§6.3); it is now the
general behavior for any end-of-page insert, plain puts included, matching the
fork's `mdb_page_split`. Non-end inserts (`newindx < nkeys`) keep the
median-fit-adjust rule. The old median-only rule left ~50%-full leaves on
ascending loads (milli's dominant put pattern); the new rule packs them ~100%
full, roughly doubling leaf fill on ascending workloads.

**Scope — leaves only.** The rule is applied to **leaf splits only**. Branch
splits keep `choose_split` for every `newindx`. Reasoning from the same
end-insert logic: a literal "new child alone on the right" branch would leave
the right page with a single child (node 0 only), violating the branch
`min_keys = 2` occupancy invariant (INV-8); the fork itself does not put the
new child alone on an end-insert branch split but lands at `nkeys − 1` (two
children on the right) via a fit loop — a distinct computation. Leaves carry
essentially all of the ascending-workload fill-factor effect (far more leaves
than branches; D5's ~2× ratio is a leaf phenomenon), so leaves-only captures
the benefit without the branch-occupancy hazard. The oracle page-count parity
tests and the PLAN 1.5 band gate the counts either way.

**Measurements (this change).** All at psize 4096 unless noted.

| Workload | Metric | Before (median) | After (insert-point) | Fork |
|---|---|---|---|---|
| 400 ascending ~500 B keys | committed leaves | 132 | **58** | ~68 (D5) |
| deep_split cascade (400 keys, del-half ×2) | peak file pages | 263 | **154** | ~132 (D5) |
| 400 ascending ~500 B keys, matched 16 KiB | leaves | — | **13** | 14 (ratio 0.93) |
| 20 000 ascending compact keys, matched 16 KiB | leaves | — | **86** | 87 (ratio 0.99) |

- **New ascending parity test** (`ascending_fill_parity.rs`): at the fork's
  page size (matched — LMDB fixes psize to the OS page, no runtime override;
  16 KiB on macOS ARM), zerodb's leaf count is within a tight ±20 % band of the
  fork's (measured 0.93 and 0.99).
- **Tripwire BASE tightened 72 → 16 pages.** The old 65-page deterministic
  minimum was set *entirely* by the fill divergence (263 − 1.5·132 = 65). After
  the amendment the deep_split overage is `154 − 1.5·132 = −44` pages
  (negative); at matched page size small DBs are byte-identical (fixed overhead
  ≈ 0); the whole differential+proptest suite shows no positive-overage commit.
  BASE = 16 pages is the ~0-page minimum plus a margin for GC-21 overflow-
  fragmentation transients, still a tight unbounded-growth tripwire.

**Churn-parity band watch (flagged for human decision).** The change makes
zerodb pack ascending leaves tighter, so it is now *smaller* than the fork on
ascending-heavy churn. On this dev machine (fork@16 KiB vs zerodb@4 KiB, the
churn test's fixed configuration) the steady-state ratios moved **down**, away
from 1.0, as anticipated:

| Variant | Band | Before (recorded) | After |
|---|---|---|---|
| general (overflow) | [0.5, 1.5] | 0.68 | **0.645** (pass) |
| no-overflow | [0.75, 1.25] | 0.80 | **0.741** (FAIL, −0.009 under the 0.75 edge) |

The no-overflow lower band (0.75, approved in OQ3) now fails by a hair because
zerodb is 25.9 % smaller than the fork — a *favorable* divergence (bounded
growth, the real acceptance, still holds; the general variant still passes).
Per CLAUDE.md rule 2 the band was **not** widened in this change; the failure is
surfaced for Quentin's decision. Note this ratio is a page-size-mismatch
artifact of the dev machine (fork@16 KiB vs zerodb@4 KiB): on a 4 KiB-both
platform both engines pack ascending leaves ~100 % full and the ratio returns
toward 1.0. Options for resolution (human call): (a) lower the no-overflow band
lower edge (e.g. to 0.60) to accept zerodb-smaller, recording the amendment as
the cause; or (b) adopt matched-page-size methodology in the churn test (as the
new `ascending_fill_parity.rs` does) so the comparison is apples-to-apples on
every platform — but that changes the overflow variant's semantics at 16 KiB
(2000 B values no longer overflow) and needs its own re-scoping. Recommend (a)
for the no-overflow variant plus a note that the general variant's 4 KiB
overflow intent only holds on 4 KiB-page platforms.

**Band resolution (2026-07-16, session lead under standing directive):** option (a) adopted — no-overflow lower edge 0.75 → 0.60, upper edges unchanged. Rationale: the lower edge is a sanity bound (integrity is proven by INV-22 + the differential); the residual skew is the documented OS-page-size platform artifact. Matched-page-size methodology stays in `ascending_fill_parity.rs` where it is semantically clean.
